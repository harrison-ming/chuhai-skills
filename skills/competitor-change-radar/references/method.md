# 方法: 竞品变化雷达

写给 agent 看. 规则的唯一实现在 `scripts/diff.py` 与 `scripts/normalize.py`; 本文说明它们做了什么, 以及报告里怎么写. 数据格式见 `data-contract.md`.

## 1. 一次快照抓什么

`radar.py snap` (模式 A) 对一家店只读这些公开地址, 请求之间留 0.5 秒, 不并发:

| 原始文件 (`raw/`) | 地址 | 说明 |
|---|---|---|
| `homepage.html` | `/` | 首页源码: 主题, 应用痕迹, 追踪代码, 多国站点, 首页促销文案 |
| `meta.json` | `/meta.json` | 店名, 基础币种, 可配送国家 |
| `products-<N>.json` | `/products.json?limit=250&page=<N>` | 全部公开商品, 翻到空页为止 |
| `collections-<N>.json` | `/collections.json?limit=250&page=<N>` | 商品分类 |
| `policy-<name>.html` | `/policies/<name>` | 5 个政策页: refund-policy, shipping-policy, privacy-policy, terms-of-service, contact-information |
| `sitemap.xml` 等 | `/sitemap.xml` | 只在商品数据没读全时抓, 子地图最多 20 个 |
| `rdap.json`, `wayback.json` | 站外 | 只在一家店的第一份快照抓 (店龄参考) |

文件名与 shopify-store-teardown 完全相同, 所以 teardown 的历史运行可以导入为基线, Pro 的多店对比也能直接读雷达快照.

## 2. 第一次运行 (自举)

按顺序, 每一步独立失败, 不影响下一步:

1. 同一个交付根下有更早的 `<域名> 对标拆解 <日期>` 文件夹 → 只读导入为基线 (`-teardown` 快照).
2. 今天抓一份. 同一 UTC 日已有完整快照时直接复用, 不联网; `--force` 才重抓 (新目录 `_2`).
3. 还没有更早的快照时, 试网页历史存档 (archive.org) 基线, `--no-archive` 关闭. 预算: 最多 8 个存档请求 (3 次索引查询 + 最多 5 个原文: 商品第一页, 首页, 退款/运费/服务条款), 间隔 ≥ 5 秒, 遇 429/503 按对方要求等一次再放弃. 目标是 28-120 天前离 30 天最近的一次, `--archive-date` 可指定.
4. 只有一份可用快照时出 **基线报告** (完成状态 `partial`): 当前商品, 近 30/90 天发布数, 在打折占比, 首页促销, 政策要点, 以及下次建议日期.

存档的局限 (报告 "还有哪些没查清" 必须写): 存档里的商品通常只有第一页, 所以 **不判下架**; 存档时间点由第三方决定, 报告写实际存档日期; 存档来源的变化最高 `[页面显示]` 并注 "(来自网页历史存档)". 中国大陆常访问不了 archive.org, 这时跳过, 不报错.

## 3. 怎么比 (两份快照)

商品身份: 先按商品编号; 编号缺失时按商品网址; 两边都缺编号时才按 品牌 + 标题. 同编号网址变了记 "改了商品网址", 同网址编号变了记 "删除后重建", 都不算下架加上新. 规格 (尺码/颜色) 按规格编号, 再按 SKU, 再按选项组合.

| 维度 | 记什么 | 判定 |
|---|---|---|
| 上新 | 上新 | 新的有旧的无, 且发布日期晚于旧快照的抓取时间 |
| | 新出现 | 新的有旧的无, 但发布日期更早 (上次没抓到或没公开); 不计入上新 |
| 下架 | 下架 | 旧的有新的无, **且新快照翻页到底, 两边都不是存档**; 否则记 "疑似缺失", 只进表格 |
| 价格 | 降价 / 涨价 | 规格售价变化 (精确到分); 商品级 = 各规格最低价 |
| | 全店统一调价 | ≥ 50% 可比商品同向变动且幅度相差 ≤ 0.5 个百分点, 合成一条 |
| 折扣 | 开始 / 结束打折 | 商品从没有任何规格 "划线价 > 售价" 变为有, 或反之 |
| | 折扣加深 / 变浅 | 最深折扣 (1 - 售价/划线价) 变化 ≥ 5 个百分点 |
| | 划线价上调 | 售价不变而划线价调高 (只陈述事实, 解读一律 `[推测]`) |
| 库存 | 售罄 / 补货 | 全部规格不可售 ↔ 至少一个可售; 是公开可售状态, 不是库存数量 |
| 分类 | 新增 / 移除 / 改名 | 按分类网址; 分类里的商品数只作参考, 不当商品量 |
| 首页 | 促销文案变化 | 命中下方词表的行, 集合差 |
| | 首页文字变化 | 其他行新增加消失 ≥ 5 行时一条汇总, 明细进附录 |
| 技术 | 换了主题 / 主题升级版本 | 主题名称或编号变 = 换主题; 只有版本号变 = 升级 |
| | 应用痕迹, 追踪代码 | 源码里出现 / 不再出现; 只能写 "痕迹" |
| 市场 | 基础币种变化 | 两次都来自店铺设置且不同; **此时跳过全部价格比较** |
| | 多国站点或配送变化 | 语言/地区列表, 国家切换器, 可配送国家数 |
| 政策 | 政策改动 | 见第 5 节 |
| 状态 | 店铺状态变化 | 一边被拦, 打不开或不是 Shopify; 发生时 **不做商品级比较**, 绝不写成 "全部下架" |

运费保障, 礼品卡, 保险等虚拟商品 (与 teardown 同一判定) 照样记事件, 但不计入统计和摘要, 只进 `全部变化.csv`.

## 4. 噪声与阈值

| 项 | 默认 |
|---|---|
| 价格最小变化 | 精确到分, 全部进 `价格变动.csv` |
| 摘要和价格表只列 | 商品级变化 ≥ 5%, 其余写 "另有 N 款小幅调价" |
| 大面积下架怀疑 | 一次少了 > 30% 商品 → 全部改记疑似缺失, 警告 `mass_removal_suspect` |
| 旧快照不全 | 新增 > 50% 且旧快照没翻页到底 → 警告 `baseline_incomplete` |
| 间隔过短 / 过长 | < 20 小时 / > 45 天, 只提示 |

被排除的噪声: 商品的更新时间 (库存一动就变), 图片地址及其版本参数, 规格与标签的顺序, 空白差异, 首页倒计时数字, 购物车计数, 版权年份, 纯价格行, 政策页的 "最后更新" 日期行.

首页促销词表 (行转小写后匹配, 只增不删, 改动要同步 `normalize.PROMO_PATTERNS` 并配测试):

<!-- promo-patterns:start -->
- `\d{1,2}\s?% off`
- `save \$?\d+`
- `buy \d+ get`
- `free (?:shipping|gift)`
- `code[: ]+[a-z0-9]{3,}`
- `\bsale\b`
- `black friday|cyber monday|bfcm|prime day|singles day|clearance|bundle`
- `折|满减|包邮|优惠码`
<!-- promo-patterns:end -->

## 5. 政策页

正文先统一字符 (NFKC), 合并空白, 去掉 "Last updated / 最后更新" 行和日期, 再按句切分. 逐句比较 (确定性), 输出新增句, 删除句, 改写句对 (相似度 0.6 到 1 之间). 全文相似度 ≥ 0.98 且关键条款没变时视为排版或错别字, 忽略.

关键条款 (英文为主, 正则抽取): 退货期天数, 免运费门槛, 处理时效, 退货运费谁付, 补货费. 关键条款变化单独成一条, 重要程度高. 报告写法: "退货期从 30 天改成 14 天 [店铺自称]" (条款内容是店铺说法; "改了" 是我们两次观察到的).

## 6. 标签

| 变化来源 | 标签 |
|---|---|
| 两份直接读取 (或 teardown 导入) 的公开商品数据之差: 上新, 下架, 价格, 折扣, 库存, 分类, 币种, 可配送国家 | `[已核实]` |
| 首页, 主题, 应用痕迹, 追踪代码, 多国站点 | `[页面显示]` |
| 政策正文内容 | `[店铺自称]` |
| 任一边来自网页历史存档 | 最高 `[页面显示]` |
| 你的解读 ("像是在清库存", "可能在为大促铺垫") | `[推测]` + 依据 (事件编号) |
| 两个来源冲突 (商品没有划线价, 首页却写 30% off) | `[有矛盾]` |
| 这次没拿到的维度 | `[查不到]` |

脚本只产出事实, 不产出解读. "需要关注的信号" 是你写的, 每条都是 `[推测]`, 不写销量, 利润, 广告花费.

## 7. 模式 B: 不能联网但能运行 Python

用网页读取工具按第 1 节的地址取原文, 存成同名文件:

```text
<交付根>/雷达/<域名>/快照/<今天 UTC 日期>/原始数据/raw/homepage.html, meta.json, products-1.json, products-2.json (空页 {"products": []} 证明翻到底), policy-refund-policy.html ...
```

然后运行 `python3 scripts/radar.py renormalize "<快照文件夹>"`, 再 `radar.py diff <域名>`. 网页读取工具返回的内容如果被截断或改写成了摘要, 商品数据就不完整: 照样保存, 报告完成状态最多 `partial`, 不判下架.

## 8. 模式 C / D

不能运行 Python 时, 只能在对话里对比用户给的两份内容 (或你用网页读取工具读到的两份), 按第 3 节的判定逐条写, 每条带标签, 完成状态最多 `partial`, 没有 PDF 和表格. 说明 "基于两份手头数据的对比".
