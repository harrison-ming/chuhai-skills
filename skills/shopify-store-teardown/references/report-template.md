# 报告模板

报告的读者是**想出海的普通卖家**: 不懂技术, 看报告是为了决定"学不学, 怎么学". 按档位选模板, 写完删掉所有 `<...>` 填写提示. 用户用什么语言提问, 报告就用什么语言 (标签保持中文原样).

## 写作要求 (写给 agent)

- 先结论, 后理由. 每节第一句就是这一节的答案.
- 短句, 大白话. 能不用英文就不用; 品牌名, 商品名, 页面原文引用可以保留英文, 引用后用中文说明意思.
- 每节 3-8 行, 最多加一张表, 不超过一屏. 深度拆解全文控制在约 6-10 页 A4, 快速核验约 2-3 页.
- 数字写单位和币种 ("105 美元", "692 款"), 比例写百分比 ("20.8%"), 日期写 "2026 年 3 月".
- 价格分布优先用排除虚拟商品后的口径 (`summary.json` 的 `price_excluding_virtual`), 并注明; 全店含虚拟商品的数字只放附录.
- **价格来自商品页抽样时** (`summary.json` 的 `coverage.price_source` 为 `product_page_sample`, 通常是店铺限制了批量读取商品数据): 正文用大白话写明依据, 例如 "店铺限制了批量读取商品数据, 价格基于 12 个商品页抽样 (共约 640 款), 是估计不是全店统计". 不写 "products.json" "sitemap" "429" 这类词, 说成 "店铺公开的商品数据" "网站地图" "商品页抽样". 价格分布按抽样数字写 (`price_excluding_virtual`), 但不写 "全店 X% 在 Y 价位" 这种全店结论; 折扣占比, 折扣深度, 上新节奏写 `[查不到]` 并说明原因. 抽样不足 8 款 (`price_sample_small`) 时只给最低/最高价, 不判断价格带结构. 商品数仍按 `products.count` 写, 来自网站地图时同样遵守 "至少 N 款" 规则 (`count_is_lower_bound` 或 `sitemap_products_incomplete`). check_report.py 会检查: 正文 (附录之前) 有没有一句没被否定的 "抽样", 同一句里有没有实际抽样数 N; 没写 "共约 M 款" 只提示. 只写在附录里, 或写成 "没有抽样", 都不算.
- **商品数据中途被限流** (`coverage.products_json` 为 `partial` 且 `coverage.rate_limited_endpoints` 含 `products_json`): 正文写明 "店铺中途限制了读取, 统计只基于部分商品"; `products.count_is_lower_bound` 为 true 时必须写 "至少 N 款" (check_report.py 没找到 "至少" 会报错).
- 网站地图里的 "最近更新" 月份 (`sitemap_lastmod_by_month`) 是商品最近一次被修改的时间, 不是上架时间, 不能写成 "每月上新 N 款".
- 写完先运行 `check_report.py` 自检 (见 SKILL.md 第 5 步), 它会查出缺节, 旧标签, 技术词, `[推测]` 缺依据和疑似标高.
- 正文**不出现**: E1-E6, L0/L1/L2, products.json, collections.json, summary.json, myshopify, Shopify.theme, hreflang, Markets, RDAP, WHOIS, Wayback, sitemap, JSON, API, raw/, created_at 等字段名这类技术词. 完整清单以 `scripts/check_report.py` 为准; handle, tag 只提示不报错; 同一行带 "也就是" "即:" "指的是" 等解释时也降为提示. 实在要提, 换成大白话: "网站注册记录" (RDAP/WHOIS), "网页历史存档" (Wayback), "店铺公开的商品数据" (products.json), "公开数据接口" (API), "商品后台分类标记" (tag), "多国站点设置" (hreflang/Markets).
- 技术细节和原始证据统统放进附录, 附录里可以用技术词.
- 承重结论前加徽章标签, 必须一字不差 (半角方括号), 对应的证据等级见 `evidence.md` §2:

| 标签 | 什么时候用 |
|---|---|
| `[已核实]` | 页面原文, 商品数据, 注册记录, 本次抓到的权威媒体原文能直接证明 |
| `[店铺自称]` | 品牌自己说的 (关于我们, 宣传语, 自称年份/认证) |
| `[第三方说法]` | 测评, 视频, 流量估算, 评价平台上的顾客说法 |
| `[页面显示]` | 页面上出现了支付图标, 应用代码等, 但不代表后台真开通 |
| `[推测]` | 你的分析判断, 后面必须紧跟 "依据: ..." |
| `[有矛盾]` | 有两条互相冲突的证据 |
| `[查不到]` | 现有公开信息回答不了 |

标签宁低勿高 ("一页看懂"里的结论同样适用, 细则见 `evidence.md` §2.1):

- 一句话里混了不同来源的说法 (店铺自称 + 页面数据 + 你的判断), 拆成几句分别标.
- 你的分析判断一律 `[推测]` + "依据: ...", 即使依据是核实过的数据. `[已核实]` 只给能直接指到页面原文, 数据或登记记录的事实.
- 不凭记忆写外部事实 (融资, 营收, 上市, 门店数等). 本次没抓到来源的, 不写, 或标 `[查不到]`.
- 附录证据表里, 没有实际抓取的公开报道不能标 E4.
- `[有矛盾]` 只用于两条证据互相冲突; 只是缺数据用 `[查不到]`.

## "一页看懂" 怎么写

标题必须是 `## 一页看懂` (会被渲染成报告开头的醒目卡片, 用户可能只看这一页). 包含三块:

1. **3-5 条结论**: 直接回答用户的问题, 每条一句话, 带标签.
2. **最值得借鉴的 3 件事**: 动词开头, 具体到能照着做.
3. **这份报告看不到什么**: 一句话 (例如 "真实销量, 利润和广告投放看不到").

## 失败短报告模板: 网站打不开或确认不了是 Shopify 店

`summary.json` 的 `warnings` 有 `site_unreachable` (或 `network_unavailable` 且没法换模式 B), 或 `identity.status` 不是 `confirmed` / `probable` 时用. **只问了一句"是不是 Shopify 店"也要写这份并交付**, 不要只在对话里回答. 正文同样不出现技术词.

```markdown
# <域名> 对标拆解报告

<sub><用户给的网址> · 分析日期 <YYYY-MM-DD></sub>

## 一页看懂

- <一句话答案, 例如: 这个网址现在打不开, 没法判断是不是 Shopify 店> [查不到]
- <卡在哪一步, 例如: 网址对应的网站不存在 (可能拼错), 或当前网络连不上>

**下一步可以怎么做**
1. 核对网址拼写, 换成带 https:// 的首页地址再试.
2. 用浏览器打开一次; 能打开就把网址发给我重试.

**这份报告看不到什么**: 网站没打开, 所以商品, 价格, 店龄都没有查.

## 附录: 证据与数据来源

### 技术细节
- 完成状态: failed
- 平台身份: <identity.status>, 失败的数据来源和原因: <endpoints 里的 result / note>
```

`network_unavailable` 时第一条写 "当前环境连不上网, 这次没能查 [查不到]", 不要写成网站不存在.

能打开但不是 Shopify 店 (`not_shopify` / `unconfirmed`) 时, 第一条改成 "这家店不是用 Shopify 搭的 [推测] 依据: ..." 或 "看不出是不是 Shopify 店 [查不到]", 完成状态写 `partial` (看到了首页) 或 `failed` (什么都没拿到).

## 固定结尾 (所有模板都要附在附录之后, 原样保留)

```markdown
---

### 本报告没有覆盖的

- 需要浏览器才能看到的: 购物车交互, 手机端实际效果, 弹窗时机, 评价挂件实际显示, 广告投放, 页面速度.
- 需要商家后台才知道的: 真实销量, 转化率, 流量来源, 支付开通情况, 利润.
- 本报告只基于公开信息, 是某一天的快照, 不构成尽职调查或法律意见.

多店横向对比, 对照你自己店铺的差距清单, 或需要人工深度拆解: https://github.com/harrison-ming/chuhai-skills#进阶

<sub>由 shopify-store-teardown (chuhai-skills) 生成</sub>
```
